# Shuttle

Shuttle runs one program, once, inside a boundary, and writes a truthful record of how the run ended.

A caller hands Shuttle one input document. Shuttle checks it, starts one executor (an AI coding agent or a plain command), stops everything the executor started, and writes one outcome record. The caller reads that record and nothing else.

## Status

Early build. It is not usable yet, and it may not be for a while. The first increment is a skeleton: `python3 -m shuttle run <input document>` runs one plain command from start to finish and writes a request record and an outcome record. The command runs in a boundary: a systemd user scope (the scope; it holds the time limit, set as its maximum runtime, and the optional memory cap, see "The memory cap") with bubblewrap inside it (the box; it holds the reach, see "The executor's reach"), with its own process space. The scope ends everything inside when the limit runs out (and when the run receives a signal: SIGINT, SIGTERM, SIGHUP, SIGQUIT, SIGUSR1, SIGUSR2 or SIGALRM), the run stops it by name and sees it empty, and reads from the scope why it ended; a reason it cannot read is "execution failed", never a guess. The time limit is a number of seconds from one microsecond to 10^9 (about 31 years): the scope's timer takes whole microseconds, and a value that rounds to zero would mean no limit at all. Arguments reach the command byte for byte: the scope tool expands `$` in the command it is given, so every `$` is doubled on the way in (the option that turns that off needs systemd 254). The boundary needs `systemd-run`, `systemctl` and `bwrap` on the machine. The run form and the check form exist (stop and status do not). The place and its two fingerprints are real (see "The place and the fingerprints"); delivery and the rest are stand-ins or not built, and a receipt field fed by a stand-in says "not built". The code and its tests are published as they are written, so the tests are the best account of what works today.

## What it will promise

- Every run ends with exactly one of seven endings: ended by itself, time limit, memory limit, stopped from outside, asked for a human, could not start, execution failed.
- What Shuttle observed is kept apart from what the executor says about its own work.
- Once the ending is known, nothing prevents a record carrying that ending.
- A request record is written before anything starts and an outcome record when the run ends, so the two together are the trace of the run.
- Each vendor's tool sits behind an executor driver, so a run looks the same from outside whichever tool did the work.

## Shape

- Outside: a command-line tool with four forms (run, check, stop, status).
- Inside: functions over plain data, in three folders. Each decision is a pure function in `shuttle/core/`. The code that gathers facts, hands them to the core and acts on the answer is `shuttle/shell/`; it touches nothing itself. Everything Shuttle does to the world (files, processes, the boundary's scope, the clock, signals, the environment, who and what it is, and the place's git repository) is one small set of operations, a record of functions typed in `shuttle/core/shapes.py` (`Operations`) and passed in; the real set is `shuttle/world/`, thin and holding no decisions. The command line wires the real set in (`shuttle/shell/cli.py`) and the process's arguments and standard streams come from the world's entry (`shuttle/world/real.py`).
- Python, standard library only.

## Refusals and the check form

- A run that cannot start ends `could_not_start` with a reason code and the step that failed. The checks are pure functions in `shuttle/core/refusals.py`, tested as tables (`tests/by_value/test_refusals.py`); the shell (`shuttle/shell/input_checks.py`, `gates.py`) gathers the facts they judge: a reference file's hash and size, whether the statement location is taken, a gate's exit code.
- The input document carries optional `instruction` with `instruction_hash` (sha256 of the instruction's UTF-8 text, given together; both are required for a kind that expects a statement and optional for a plain one), `references` (name, path, hash, size, hash_source), `gates` (name, command, arguments, limit_seconds), `statement_location`, `reach` (optional: `{"visible": [folders]}`, see "The executor's reach"), `memory_limit_bytes` (optional, see "The memory cap") and `place` (required: the path of a linked working copy of the caller's repository, see below). Not yet built from the design: the destination and branch checks, the records-location mismatch check (the design does not say how Shuttle can know a repository's records location, so there is nothing to compare yet), folder references (a folder is refused as missing, and the message says it is a folder).
- Kinds are read from two files shipped with the code, `shuttle/data/kinds_with_statement.txt` and `shuttle/data/kinds_without_statement.txt`; a kind on neither is refused, and so is a run whose files cannot be read. A kind that expects a statement needs a `statement_location` that does not exist yet and is not in the records folder (`statement_location_in_records`: refused when the location, resolved through links and `..`, is the records folder or below it, so Shuttle never writes a caller-named path among its records; the line reads "statement_location '<path>' is in the records folder, where Shuttle writes only its own records; name a path outside the records folder"); a kind that expects none and is given one is refused (`unknown_field`).
- Gates run in order before the executor starts, each with PATH only in its environment (and what systemd itself sets, such as `INVOCATION_ID`), each in a systemd user scope of its own with its limit as the scope's maximum runtime: nothing in the command times a gate. After a gate the scope is stopped by name, seen empty and forgotten, and why it ended is read from it. Exit 0 is yes, exit 1 is no; any other exit, a passed limit, a scope that was not seen settled or a failed start is failed. The scope's tool exits 1 when it cannot make the scope, which would read as a no, so the gate's command is started through one line of shell that says on a pipe that it is about to start; a gate that never said so is failed. The first answer that is not yes refuses the run, and its name and answer are the reason text.
- The request id may be left out: one is generated and printed first. An id is used once: a run is refused when its request record or its outcome record exists, and neither is touched. That refusal, a document too broken to form a header, and (awaiting the owner's decision) a document holding a credential-like environment value write no record at all, print one line on standard error, and exit non-zero; the last is refused before the id is claimed, so no record keeps the value and the id is not spent. The check form still reports `credential_like_value` for it.
- `python3 -m shuttle check <input document>` runs every check a run would make, including the gates and whether the id is used and the records location is a folder that exists and can be written, and launches no executor (it does start the gates, which are read-only by their nature), writes no record and claims no id. It prints the request id, then (when it found a refusal) the outcome record the run would have written, on one line, then `check: no refusal found` or `check: refused: <reason>`, then a last line saying that passing is not a promise. Exit 0 means the check ran to its end, passing or refusing; non-zero means the document could not be read far enough to check.

## The place and the fingerprints

- The input document's `place` is the path of a linked working copy of the caller's repository, made by the caller for this run. A run is refused, before anything starts and in the check form alike (reason, failed step `input_check`), when the place is not a folder that is there (`place_missing`; a document with no `place` is the same), is not the top of a git working copy with at least one commit (`place_not_a_git_checkout`; a folder inside a checkout is not one), has a tracked file that carries a `filter` attribute, from `.gitattributes` or the repository's `info/attributes` (`place_has_filter_attribute`; filter drivers are not supported and never run, so such a place is refused whatever the index's timestamps are, with one such path named), holds a repository of its own below its top, whether git ignores it or not (`place_has_nested_repository`, named before the uncommitted file git also reports for it), or has uncommitted, staged or new unignored files (`place_has_uncommitted_changes`). The place is looked at again just before the executor starts, since the gates ran in between: a place that is no longer clean is a `freeze_failed` at `opening_freeze`.
- The opening fingerprint is the place's own commit. No commit is made at the start. The closing freeze is one commit of the place's files as they are, made by Shuttle to the reference `refs/shuttle/freeze/<request id>` in the place's repository, with the opening commit as its parent, under the name "Shuttle", no address and a fixed date, so the same files give the same commit. It is taken only when the executor's boundary was seen empty. It holds every file that the ignore rules of the working files at the time of the freeze do not exclude (the design says the opening commit's rules; the owner is deciding, and today's behaviour is the working files', so a script that ignores a file as it writes it leaves it out of the freeze), whatever the place's own history says: a script that makes its own commits, moves the branch or resets it does not move the closing fingerprint, and a commit made by the executor is never the freeze. Files equal to the opening commit's give the opening commit itself (nothing is made), the receipt says `changed_nothing`, and the counts are zero; otherwise the receipt counts files added, changed (a change of type counts) and deleted against the opening commit. A link is frozen as a link and never followed; a repository cloned into the place during the run is frozen as one entry naming its commit; a file that cannot be read, a folder that git cannot enter (its files would otherwise be left out without a word), or any other failure of git, is a failed closing freeze (`execution_failed`, `closing_freeze_failed`, failed step `closing_freeze`) with the opening fingerprint only.
- No command from any configuration runs in Shuttle's git work: not a filter driver (`clean`, `smudge` or `process`) defined in the repository, added to it by the executor during the run, or defined at user or system level. The place check reads attributes (which runs nothing) before it compares anything. The freeze adds the files in a scratch git directory with no configuration, whose working tree is the place and whose objects are the place's, so no driver exists there to run, and a file the script added under a filter attribute is frozen as its bytes on disk; only `update-ref` runs in the place's own repository. The freeze therefore reads none of the repository's own settings (such as `core.filemode`); it does read the place's `info/attributes` and `info/exclude`. Every git call is given exactly the environment `shuttle/core/place.py` builds: PATH only from the caller's, no global or system configuration, no hooks, no signing, no editor, no prompts, no ignore file or attributes of the caller's, the place's own settings for those overridden, the neutral identity, and no write to the caller's index when only looking. The freeze uses plumbing on a temporary index of its own, so the caller's branch, index and settings are untouched; its only write to the repository is its commit's objects and its reference. Freeze references stay in the repository: one per run that changed something, never removed, and they show in `git for-each-ref`, in `git log --all` and in a mirror push (`git push --mirror`; not in `--all` or `--tags`), so a caller who mirrors publishes the frozen files.
- The freeze's git work is one command run to its end in a scope of its own, with the limit on the scope, the way a gate is run: nothing in the command times it. Its limit is the document's optional `freeze_limit_seconds` (the same bounds as the time limit), and the run's own `time_limit_seconds` when that is left out: the design gives no value for it, so none is invented (awaiting the owner).
- The executor's working directory is the place (bubblewrap's `--chdir`).
- Git is reached only through the `git` group of the operations (`look_at_place`, `freeze`); the real set is `shuttle/world/git.py`, the simulated one is held to it by the contract cases.

## The statement and the references

- The statement's schema is data, defined once in `shuttle/data/statement_schema.json`, so a second program (the check on a builder's hand-off) can read the same file. Its fields: `claim` (one of `done`, `partly_done`, `blocked`, `not_done`), `summary` (text), `evidence` (a list of items, each a `claim` and a `command` to run, not a pasted log), `not_tested` (a list of text, empty when nothing was left out) and `feedback` (text, on the input). Every field is required and no other is allowed. `shuttle/core/statement.py` judges a statement's bytes against that data by hand (no library), and `tests/by_value/test_statement.py` is the table of accepted and rejected statements.
- The executor is not given the document's `statement_location`: not in the notice, the instruction file, the arguments, the environment or the run area. (The request record in the records folder holds the whole input document, so that folder is hidden from the executor, see "The executor's reach".) A tool that writes its statement as a file writes it at one path inside the run's own run area, `shuttle-statement.json` (`STATEMENT_NAME` in `shuttle/core/run_area.py`; no setup request may use the name), which the notice gives it. After the run, the file the executor left at that path is copied byte for byte to `<request id>.statement.kept` beside the records, and that copy is hashed and judged. Execution never tidies or completes it. The receipt's `statement_state` is `none` (the state: nothing was left), `right_shape` or `wrong_shape`; `statement_hash` and `statement_location` are the kept copy's; `claim` is the claim word as written when the shape is right and `none` otherwise. Where a wrong-shaped statement is reported beyond that state is not specified, so nothing more is built. A file that could not be kept or read leaves the four fields `cannot tell`. The kept copy is then copied to the document's `statement_location`, where nothing is replaced (a name that appeared there during the run is left, and what was kept and judged does not change); `shuttle/shell/move_kept_files.py` is the one place a statement leaves the run area, whatever the driver. A file written directly at `statement_location` and not at that path is not a statement: the state reads `none`. The copy goes into the folder the location's parent resolved to when the run began, and only when the stop is confirmed and the parent still resolves there: a parent the executor swapped for a link is not followed, and nothing is written (the kept copy and the receipt are unaffected). A location is used once (a second run naming it is refused as occupied, as before). Only a regular file is kept: a link (never followed), a named pipe, a device, a socket or a folder at that path reads `wrong_shape` and nothing is copied. The run area is made for every driver, the command driver's included (it asks for no setup, so it holds the instruction file and what the executor writes).
- The notice (`shuttle/core/notice.py`, version `NOTICE_VERSION` in `fixed.py`) is added after the instruction of every kind: where each reference is, that a reference wins over a file of the same name in the place, and that the executor cannot commit in the place; a kind that expects a statement also gets where (the path in the run area) and how to write it, or, for a driver whose statement is its tool's final message (`STATEMENT` is `reply` in the driver; `file` for the command driver), that the statement is the final message, in the schema's shape and nothing else. A plain kind with no instruction is given the notice alone. The instruction and the notice reach the executor as its standard input, never on the command line: the launch step writes them to a file in the run area (below) and the process operation `start` gives that file as the child's standard input (a start with no such file gives the null device, as before; standard output and standard error go to the null device too, unless the driver's launch names a file for standard output, which `start` makes new).

## The run area

- The run area (`shuttle/core/run_area.py`, steps `shuttle/shell/set_up_run_area.py` and `shuttle/shell/tear_down.py`) is a folder made for one run in the system's temporary place (`TMPDIR` when set), named `shuttle-run-area-` and the run's own part of its scope names (`run_area.area_name`; the part is the id in the run's request record), private to its owner and removed whole at every ending the command lives to see, including a run refused after the set-up, a stop that was not confirmed and a signal. If Shuttle itself is killed (SIGKILL cannot be handled), its run area stays in the temporary folder with the instruction file in it, which holds the instruction text and the notice, and with the executor's own home, which holds what a driver copied there (the Codex driver's copy of the login, with the mode of the original); nothing sweeps such areas yet. A removal that fails is the receipt's `teardown_failure` and changes no ending. Beside the area, in the temporary folder and not in the area, is a lock file of the same name and `.lock` (`run_area.lock_path`), made and locked before the area is made, held (an exclusive `flock` the world's `create_lock` takes) to the end of the run, and removed after the area is: so the area is never on disk with its lock free, and the kernel gives the lock back when the process dies, a hard kill included, with no help from it. The box binds the area and not the folder above it, so the lock file is not there for the executor, which cannot see or open it; a child the run starts does not inherit the lock. An area that could not be removed keeps its lock until the process ends. A lock file that could not be removed is no failure of the run: it is a leftover, which the sweep (below) removes.
- A driver's setup requests are data: copy a named path in (leaving named parts out; a copy may be `optional`, left out when its source is missing), write a generated file, make a path writable, pass a variable (a text, or the path of a name in the area). Names are inside the area and cannot climb out. Nothing is shared by a link, because the box hides the caller's folders and a link to one would lead nowhere inside it; a driver that needs a file of the caller's copies it, and the copy goes with the area. Every area starts with two empty folders of its own, `home` and `tmp`, which the box gives the executor as its `HOME` and its `/tmp`; a request may put things under `home` and may not make `home` or `tmp` themselves. The setup actions are copy, leave out, write, make writable and pass a variable; the steps are plain file operations done before the box starts. Each action is one block in `shuttle/core/run_area.py` (its fields' check and the steps it becomes) found by name in the `ACTIONS` table, and the rules between requests are in `plan`. A new action is a block and a table entry, plus its name in `SetupAction` and its fields in `SetupRequest` (`shuttle/core/shapes.py`), and a step kind with its case in the shell only if it does something no step does, or a role only if it follows a rule no role has; a test fails for a name with no table entry. The core turns the requests into a plan of whole paths or refuses all of them; the shell acts through the file operations. The command driver asks for nothing; the Codex driver's requests are under "Executor drivers".

## Executor drivers

- A driver is a module under `shuttle/core/drivers/` offering what `interface.py` lists (there is no base class). `table.py` maps the name the document gives (`executor.name`) to its module and is the only place that names a driver: the document check, the run's steps and the check form all go through it (`shuttle/shell/the_driver.py` in the shell). A name not in the table is refused as `unknown_executor`. Adding a driver is one module and one table entry (a test fails for a driver module with no entry). A driver never names an ending: it says what it saw, and the decisions read that.
- The check form looks, for whichever driver, at every source the driver's setup copies (except an `optional` copy's) and refuses a missing one as `setup_failed` at step `setup` with a line naming it, the verdict a run's own set-up reaches for a source that is not there. A copy may be marked `follow`, which the Codex driver does for its login: the source is first resolved through links, and the file it leads to is looked at and copied (a login kept elsewhere and linked to is copied as the file it leads to; a link to nothing is refused by the check and the run alike). Otherwise it only looks that the name exists, so a source that is a link to nothing, a link, a pipe or a device (and, for a `follow` copy, a pipe or a device at the end of the link) passes the check and fails the run's set-up (the run then ends `could_not_start` before launching, with a line that names the source and says to give a regular file the run may read); a run still ends the same way if the file goes missing between the check and the run.
- The document's two standard settings are the optional top-level fields `network` (`on` or `off`) and `changes_to_place` (`allowed` or `not`). `changes_to_place: not` is enforced by the box for every driver: the place is read-only in it (see "The executor's reach" below), and the Codex driver also keeps its own sandbox's mode. The command driver refuses `network: off`, which nothing enforces for it yet (`unknown_setting`, in the check and the run alike); `network: on`, `changes_to_place: allowed` and neither named work as before. A value that is not one of the words is `unknown_setting`. The Codex driver's check refuses a document that leaves one out (`missing_setting`), and its launch command maps them onto the tool's own sandbox: `changes_to_place` allowed is its workspace-write mode and not allowed its read-only mode, and `network` is the workspace-write sandbox's network setting. The read-only sandbox has no network setting, so this driver's check refuses `network: on` with `changes_to_place: not` (`unknown_setting`).
- The Codex driver (`shuttle/core/drivers/codex.py`) takes the settings its `settings_refusal` accepts. Its check refuses a document whose settings, program or login the tool could not run with; the shell only looks whether the login's name is there and never opens it. Its setup asks for a tool home (`.codex` in the executor's own `home` folder in the run area) holding the settings file copied (when there is one: the tool starts without it, so that copy is `optional` and left out when its source is missing) and the login copied, a folder for saved output, and the variable that points the tool at its home; the tool saves a refreshed login by writing a temporary file beside it and renaming over it, with lock files in the same folder, so the login must be a file in a folder the tool can write, which a link or a single bound file is not. The original login is never changed: nothing is copied back, so a login the tool refreshes during a run is lost with the area, and the next run starts from the caller's own; nothing else of the caller's tool home is taken, so its history, sessions and caches are left behind by never being named. Its launch command runs the tool in its exit-when-done mode with the instruction on standard input, its event stream written to a file in the run area (the `output_to` of the process operation's `start`) and its final message to another.
- After the run the `observe` step hands the driver those two files and the driver gives back the receipt's `executor_driver` group and whether the tool gave a final message; when it did, the step copies that file to the statement path in the run area (when nothing is there) so the step that keeps and judges the statement treats it like any other. The saved files are read a line at a time through the file operations' `read_lines` (a line is bounded by `LINE_LIMIT` in `shuttle/shell/the_driver.py`; a longer one is cut, its rest skipped, and a field it may have held reads `cannot tell`), so what is held does not grow with the file and the stream's total size has no limit. A field the saved text lacks reads `cannot tell`, and the fields taken from the tool's session record read that until a real run can find it (no step lists the tool's session folder yet). The receipt's `waiting_question` is the final message's last line that is not blank, when it ends with a question mark. A final message that is a question is not a statement of the right shape: the statement is `wrong_shape`, and the ending is the decisions' (`ended_by_itself` when the tool exited by itself).
- No test starts the tool or opens a login. The one real-run test of it (`tests/boundary/test_tool_output.py`, and `test_login_copy.py` for the login's copy) runs through the harness helper `run_a_stand_in_tool` (`tests/rehearsal/real_run.py`), whose docstring holds the guard that keeps a real tool from starting; the stand-in's folder is made visible through the document's `reach`, as a caller would for a tool in a hidden folder. The rule test (`tests/by_value/test_no_codex_in_the_suite.py`) refuses a file that can start a process and names the program, so that test never holds the name. The driver's own tests (`tests/by_value/test_codex_driver.py`, `test_executor_drivers.py`) run on plain data and the simulated world with a stand-in program, reading small hand-made files in `tests/by_value/saved_output/` that follow the shape of the tool's output with made-up identifiers and counts.

- Every reference's path is visible to the executor, read-only (see "The executor's reach"). The receipt's `reference_hashes` is each reference's hash by name, as the check before the start found it; `none` when the run was refused or has no references.

## The executor's reach

The reach is what the executor can see and write. It is hidden unless declared. It limits the damage of an agent that is lost or confused; it is not a security sandbox, and it holds nothing against a program that means to get out (the network is shared, a user namespace can be made inside the box, and a read-only mount is only as safe as the kernel). The box (`bwrap`, in `shuttle/core/boundary.py`) is given:

- Read-only: `/usr` and `/etc` whole, and `/bin`, `/sbin`, `/lib` and `/lib64` where the machine has them (a link into `/usr` on most, a folder on some; a "try" bind follows the link and is skipped where the name is not there, so one list serves each layout). Where `/etc/resolv.conf` is a link to a file outside `/etc` and `/usr` (systemd-resolved's or NetworkManager's file under `/run`, the usual setup), the link would lead nowhere in the box and a bind cannot be made onto a link, so the shell resolves it and the file it leads to is bound read-only at its own path, a snapshot taken at the start; the rest of `/run` is not there. Where the file is a plain one in `/etc`, there is none, or the link leads nowhere, nothing is bound for it, and lookups may fail in the box.
- `/dev` and a `/proc` of its own.
- The executor's own `/tmp` (the run area's `tmp`) and its own home (the run area's `home`, with `HOME` set to it), both gone with the run area. A real `/tmp` is never shown: a folder listed as visible that is or holds `/tmp` is refused (below). This bind comes before every path below, because a later bind over `/tmp` hides an earlier bind of anything under the real `/tmp`, where the place, the run area and the folders of this suite's tests often are.
- Read-only, each: the folders the document lists as visible, each reference, the place's git folders (below), and the place itself when the document says `changes_to_place: not`.
- Writable: the run area, and the place unless the document says `changes_to_place: not`.
- The place's git folders are read-only: a plain checkout's `.git`, and for a linked working copy its own git folder and the one it shares with the checkout it was made from, each at its real path (the shell asks git for them). Nothing else of that checkout is shown, so its working files stay hidden. So in the box git reads (`git status`, `git diff`, `git log`) but cannot write: `git add`, `git commit`, a change to the git configuration and a new file in the hooks folder all fail. A writable `.git` is not offered. An executor that tries to commit sees git's own error that it cannot create a file under `.git` (for example `Unable to create '.../index.lock': Read-only file system`); Shuttle does not detect that case. The executor still changes the working files, and the closing freeze, which runs outside the box, records them.
- The paths above are bound shallowest first, so a path under another is not covered by it, and a path that is both visible and the place is writable when the place is.
- Hidden, because never bound (and a listed folder that is or holds the user's home folder, the user's runtime folder, `/tmp`, `/proc` or `/dev` is refused, so a listing cannot undo it): the user's home folder, other checkouts, `/run/user/...` with the user's systemd and D-Bus sockets (the two variables that name them are also taken out of the executor's environment unless the caller named them), the real `/tmp`, and the records folder, request record included. Where the records folder is inside something that is bound (the place, a reference), an empty folder is mounted over it.

The box's mount points are made on the host inside the folders it binds from, so the executor's `/tmp` starts with the folders that lead to the place and the run area when they are under the real `/tmp`, and it goes with the run area.

The input document's `reach` field is optional. It is an object with one member:

- `visible`: a list of absolute paths of folders to make visible, read-only. A document can make nothing writable and can never make the records folder visible. Read-only is a property of the mounts: a socket in a listed folder can still be connected to, which is why the user's runtime folder is refused. A folder inside the user's home folder may be listed (the specific folders a tool needs); the home folder itself, or a folder above it, is refused because it would show all of it, keys and credentials included. The home folder and the runtime folder are the ones the system gives the user (the account's record and `/run/user/<uid>`), never the ones the caller's `HOME` or `XDG_RUNTIME_DIR` name, so a caller's environment cannot switch these refusals off. A caller whose tool is installed in a hidden folder (a version manager's folder under the home folder, `/opt`) lists that folder; the executor's `PATH` is the caller's own and is not changed.

Left out, `{}` and `{"visible": []}` add nothing. Anything invalid is refused at the input check, in the check form as in a run, with one line that names the path and what to do (the reason, then the line):

- `reach_not_valid`: "reach is not an object; give {"visible": [<absolute paths of folders>]} or leave it out", or "reach.visible is not a list of paths; give the absolute path of each folder to make readable, as text".
- `unknown_field`: "reach has 'x', which it does not take; its only member is visible, a list of absolute paths of folders to make readable".
- `visible_not_absolute`: "reach.visible 'p' is not an absolute path; write it from the root, starting with '/'".
- `visible_missing`: "reach.visible 'p' does not exist; give a folder that is there, or take it out".
- `visible_not_a_folder`: "reach.visible 'p' is not a folder; list the folder that holds it, or take it out".
- `visible_overlaps_the_box`: "reach.visible 'p' is or holds '/tmp', which the box makes its own for the executor and a listed folder would cover; list a folder under it, or take it out" (also for `/proc` and `/dev`).
- `visible_overlaps_the_runtime_folder`: "reach.visible 'p' is or holds the user's runtime folder 'r', where the user's systemd and D-Bus sockets are, and they stay hidden; list a folder that does not hold it, or take it out".
- `visible_overlaps_the_home_folder`: "reach.visible 'p' is or holds your home folder 'h', which would show all of it (keys, credentials, other checkouts); list the specific folders the tool needs instead, or take it out".
- `visible_overlaps_the_records`: "reach.visible 'p' is, holds or is inside the records folder, which stays hidden whatever is listed; list a folder that does not touch it". Paths are compared after links and `..` are resolved, as the box binds them.

The program the run needs is checked the same way, in the check form and the run alike, at the executor driver check, for every driver (the Codex driver's tool as the command driver's command). The shell asks the world where the caller's machine finds it (`processes.find_program`, the absolute path as found, a link not followed) and what that path leads to once links are resolved (`boundary.resolve`), and the core (`boundary.hidden_program`) refuses it when the box would not show the file: `program_not_visible`, with a line that names the folder that is hidden and says to list it under `reach.visible`. The box shows the file when both the path found and the file it leads to are under a system folder (`/usr`, `/etc`, `/bin`, `/sbin`, `/lib`, `/lib64`), the place, a reference, a folder listed in `reach.visible`, a git folder of the place, or the file `/etc/resolv.conf` leads to; `boundary.shown_paths` says this from the same pieces `box_arguments` binds, and a test holds the two together. A link in a shown folder that leads into a hidden one names the folder the file is really in; a link in a hidden folder names its own folder, since the box does not show the link. A path that goes through a link in its folder (a `latest` link to a version's folder) is not a path the box has, because the box binds the real folder: the line says the box has the file only at its real path, and to name that path as the command (or put its folder on `PATH` in place of the link's) and, where that folder is not shown yet, to list it; a caller who names that real path as the command ends with a document the check accepts, and so does one who puts the real folder on `PATH` unless the program file there is itself a link to a differently named file in another folder, which the check then judges as that link. A path with extra leading slashes (`//bin/sh`) is the same file as its plain spelling and gets the same answer. A line never tells the caller to list a folder the listing itself refuses (the records folder, the home folder or a folder holding it, `/tmp`, `/proc`, `/dev`, the runtime folder; the tests are the reach check's own): it says the folder cannot be listed and the program has to be in another one. A program that is not found at all is still `tool_not_installed`. The program is judged only once the input checks have passed: a document refused for its place, reach or references has no reach to judge it against, and is refused by those checks alone.

What this check covers: the program file itself. It does not look at an interpreter a script names (a `#!` line), at libraries a program loads, at a link in the middle of a chain of links, at `..` after a link (it is read as text, not as the kernel reads it), at a relative command (it is found from the caller's folder, and the box runs it in the place), or at anything else the program opens by itself from other hidden folders. Of those, what the box cannot execute at all is told apart after the start ("The records", the program the box could not start; what is not told apart is listed there too), as real runs show for a script whose interpreter is hidden, one whose interpreter is missing and a `..` after a link into a hidden folder; the run ends `could_not_start`, reason `program_not_started`, step `launch`. What starts and then fails by itself stays the program's own exit, and that includes a program whose library is hidden or missing: the dynamic loader, which runs after the program is executed, reports it as the program's exit 127 (shown by a real run), and nothing the box offers tells it from a program that exits 127 itself. A program that sits directly in a folder that cannot be listed has to be moved into a folder of its own.

Gates and the closing freeze run in a scope with no box, so they see the whole machine as before.

## The memory cap

- The input document's `memory_limit_bytes` is optional and has no default: Shuttle carries no number of its own. Left out, the run has no cap and the machine is not asked anything. It is named in bytes, like the other quantities (a key that holds one names its unit), and it is a whole number from 1 to 2^62; anything else (zero, a negative or fractional number, `64.0`, text, a truth value, a number above the top: the scope reads 2^63 - 1 and more as no cap at all, and the top is kept well below that) is refused as `missing_setting` at `input_check`, in the check form and the run alike, with a line that says what the setting takes and that leaving it out runs without a cap. The kernel holds a cap in whole pages, so a cap of a few bytes is a cap that nothing can run under. A cap smaller than the box itself needs ended the run as `memory_limit` in the runs tried by hand (see the pull request description).
- The cap is held by the scope: `MemoryMax` set to the number, and `MemorySwapMax` set to zero, so memory and swap are capped together. With swap left open a program over the cap is only slowed (the pages go to swap) and nothing ends; with none, going over it ends the run. Shuttle sets no other policy: the scope's default is that when the kernel kills a process for the cap, the scope stops everything in it and its result is `oom-kill`. The cap is on the executor's scope only: a gate and the closing freeze are run without one.
- A capped run whose executor went away by itself has its scope read, a bounded number of times (`SETTLE_READS` in `shuttle/core/boundary.py`), one read after another, until the scope has ended, and only then stopped. The manager ends a scope for the kernel's kill as `oom-kill` a little after the kill, and a stop that arrives first replaces that with a success, so the evidence is gone and a run killed for a very small cap would read `could_not_start` with `launch_failed`. The bound is a count, not a time, so a scope that really is still running (a stray process) is stopped after the reads, never waited on. Nothing in the code proves the window closed for every cap and machine. A run with no cap reads the scope once, after the stop.
- `memory_limit` is the seventh ending, with the reason `memory_limit` and no failed step: the boundary ended the run at a limit the caller set, as `time_limit` is for the time. It is decided from the scope's own result only (`oom-kill`, read after the scope was stopped, on a scope that was started with a cap), never from bubblewrap's report or an exit code, which can be the same for a program the cap ended and a program the box never ran (when bubblewrap was ended with the scope), so neither can tell them apart. A run with a cap whose program was never reported running ends `program_not_started` (its scope ended by itself with a success), one that reaches the time limit ends `time_limit` (the scope's result is `timeout`), one that stays under the cap ends as its own exit, and a stop or a signal comes first as it does for every ending. `tests/boundary/test_memory_limit.py` runs for real the cases over the cap, no cap, under the cap, the time limit and a program not started, on programs that allocate in steps; `tests/by_value/test_memory_limit.py` holds those by value, and `tests/by_value/test_waiting.py` the order of reading and stopping for a stop or a signal.
- What the receipt holds for `memory_limit`: the ending and reason, with a reason line that says the run was ended when the kernel ended a process in it under the memory cap of <n> bytes (the document's `memory_limit_bytes`), which exceeding the cap does and a shortage on the whole machine during a capped run does too, and that files in memory-backed storage count, `everything_stopped` true (the scope was stopped by name, seen empty and, because a scope that failed stays loaded until it is reset, forgotten; the run area is removed), the closing freeze and the counts of what changed in the place as for `time_limit`, and no exit code and `cannot tell` for the signal: what bubblewrap reports then is either nothing (it was ended with the scope) or `128 + 9` (it saw the kill first), and neither is the program's own exit, so the number is never claimed. The peak memory field is `not built`, as the Status section says.
- Files count against the cap where they are kept in memory: files written to the box's temporary folder (the run area's `tmp`), or to the place or run area where they sit on memory-backed storage such as a `tmpfs` `/tmp`, count against the cap (a program that allocated nothing and wrote files there ended `memory_limit`; the observation is in the pull request description).
- A document that names a cap on a machine that cannot hold one is refused before anything is launched, in the check form and the run alike (reason `memory_cap_unavailable`, failed step `input_check`), with the line "memory_limit_bytes is set, and this machine cannot cap memory for a user scope (a trial of a short scope with a memory cap failed: the scope could not be made or read, or it did not hold the cap); leave memory_limit_bytes out of the document to run without a memory cap". The machine is asked by a trial: the world's `try_memory_cap` starts a short scope of its own with a cap of 64 MiB and no swap, and reads back what the scope's cgroup holds as `memory.max` and `memory.swap.max`; the machine can cap only when both read back exactly the numbers it was asked for. A trial that cannot be made or read, or reads `max`, is a machine that cannot (a user manager without the memory controller delegated to it, or a machine on the older cgroup layout). There is no "cap if possible, otherwise run anyway": a caller who wants the run on such a machine leaves `memory_limit_bytes` out. The trial is started only when the document names a cap.
- A scope that ends `oom-kill` with no cap named is the machine itself out of memory, not a limit anyone set, and it is not `memory_limit`: it ends `ended_by_itself`, the executor having gone away by itself, (with the exit code bubblewrap reported, or none), unless a stop or a signal came first. Nothing in the record says the machine was out of memory; Shuttle does not read the scope's result for anything else. The one case this does not tell apart: a machine-wide shortage that kills a process inside a scope that also has a cap gives the scope the same result, so it reads as `memory_limit`; Shuttle does not read the scope's peak to tell the two apart.
- Out of scope here: the peak memory on the receipt, a default cap, a "cap if possible" mode, processor or process-count limits.

## The records

Two records are written per run, both JSON:

- A request record (a header, and `input`, the exact text the caller gave, nothing rewritten or dropped, a duplicate key included; the receipt's `input_hash` is over those same bytes, so it can be checked from the record alone) before anything starts, and an outcome record (a header, and the receipt) when the run ends.
- Every field of the receipt is a pair, `{"state": ..., "value": ...}`: the state says how the value is known, so a field whose own text is the word "none" is not mistaken for the state "none".
- The four states, in the one list of fixed values (`shuttle/core/fixed.py`, `STATES`), are `value` (execution looked and found this), `none` (it looked and there is nothing), `cannot tell` (it could not look) and `not built` (the step behind the field is still a stand-in; when the last stand-in is replaced, the state is removed from the list).
- Only the state `value` carries a value; the others carry `null`.
- The executor's exit code is what bubblewrap reports for it, and bubblewrap reports a child killed by signal `n` as `128 + n`, the same as a script that exits with that number; its status report (`--json-status-fd`) uses the same encoding, so nothing the boundary offers tells the two apart. The receipt keeps the exit code as observed and says `cannot tell` for `signal` in every run whose executor ran in the boundary; it never reads a signal out of a number. A run in which the executor never started (bubblewrap's report has no `child-pid`: a tool missing or refused, no user manager, no user namespaces) ends as could not start, reason `launch_failed`, with no exit code and no signal. A run in which bubblewrap reported the executor forked and never reported the program running ends as could not start, reason `program_not_started`, with no exit code and no signal. That has two causes the report does not tell apart: bubblewrap could not execute the program (a missing or hidden file or interpreter), or bubblewrap failed while making the box after the fork (a listed folder or the place gone since the check). `reason_text` says what was observed, names the program, and gives both things to look at: the program and its interpreter, and that every folder the document lists and the place still exist. The two are told apart by facts, never by an exit code: bubblewrap writes `exit-code` to its report only for a program it executed (it keeps a pipe that closes when the program is executed; the function that does this was read in the sources of 0.6.2, 0.8.0, 0.9.0, 0.10.0 and 0.11.0, and the real tests have run on 0.13.1 and on the hosted job's 0.11.1, no others), so a report with `child-pid`, no `exit-code`, a scope that ended by itself and bubblewrap's own failure status 1 (`boundary.program_not_started`) means the program was not reported running (never executed, or the box failed after the fork), and a program that was executed and exited 0, 1, 126, 127 or any other code has its `exit-code` line and is reported as its own exit (`tests/boundary/test_program_not_started.py` runs each of those). Nothing is added in the box for this: no process, no file, no descriptor, and the executor's output and exit code mean what they did. What is not told apart: a program that is executed and then fails by itself looks like the program's own exit, whatever the cause (a missing library at load time, above); and a file the kernel will not execute but `execvp` hands to `/bin/sh`, which is executed, as the shell, and ends as its own exit (an ELF for another architecture, a file with the execute bit and no `#!` line, a script whose `#!` line is so long that the kernel cuts the interpreter's path, or one whose interpreter is an ELF for another architecture (one run by hand ended with `exit-code` 0, the intended interpreter never started): exit 126, 127, 1 or even 0, the intended program never having run; `tests/boundary/test_program_not_started.py` pins the first); a bubblewrap ended from outside (a signal, another status) is not read either way and stays as it was; the time limit, the memory limit and a stop are decided first and are not changed. Adding a value to the fixed lists changes `RECORD_VERSION` (`shuttle/core/fixed.py`); the input version changes only for a value the document may name, and `memory_limit_bytes` is a field, not a value.
- The receipt has four groups, keyed `ending` (the ending, its reason and the receipt's id), `execution` (what execution itself saw, with its own version and the host), `executor_driver` (what the executor driver observed) and `executor` (what the executor said).
- The input document and the records carry separate version numbers, `INPUT_VERSION` (the document's `format_version`) and `RECORD_VERSION` (each header's `record_version`), in `shuttle/core/fixed.py`; each is checked on its own, and the first version makes no compatibility promise.
- Records sit beside each other in the records location, named `<request id>.<kind>.json`, with the four kinds (`request`, `outcome`, `stop`, `liveness`) in the one list of fixed values (`RECORD_KINDS`) and every name made in one place (`record_name`).
- Only the request and outcome records are written; the names of the stop record and the liveness file are reserved and nothing more is defined for them.
- A request id cannot hold a dot.
- A receipt is built only from pairs: a bare string where a pair belongs, or a field left out, is refused.
- A step says "looked, found nothing" by returning an empty value (an empty text, list or dictionary); a key it leaves out, or `None`, reads as "cannot tell".
- What execution observed is turned into pairs without ever handing the builder one it refuses: an empty text (an empty host name, say) is `none`, and anything JSON cannot hold, or a number that is not finite, is `cannot tell` for that field alone.
- If the builder still refuses, the run says so in one line on standard error, naming the fields, and writes the minimal receipt (the ending, and `cannot tell` for every other field).
- A value whose state is `value` is plain JSON, and in the ending group the words `none`, `cannot tell` and `not built` are said by the state, never held as a value.
- A key that holds a quantity names its unit: `duration_executor_seconds`, `processor_time_seconds`, `peak_memory_bytes`.

## Checking a change

One script decides whether a change is sound: lint (ruff, including a limit of three nested blocks and a ban on importing any library that reaches the world anywhere under `shuttle/` except `shuttle/world/`, and on the core importing the entry file; the other import rules between the folders are the rule test's, in the tests), format check (ruff), strict types (mypy, over `shuttle/` and `checks/`), the by-value tests (`tests/by_value`, under a 20 second budget that keeps the logic tests fast) and the tests that start real processes (`tests/command` then `tests/boundary`, a stage of their own under a 120 second budget that ends a test that never returns; it stops at the first folder that fails, so a failure in the first means the second did not run). The real stage also runs under a file-size limit and an address-space limit set once in the script (when the shell's own limit is lower it ends `check: could not run`, exit 2), and the command the harness in `tests/rehearsal/real_run.py` starts has tighter ones; the by-value tests start no process and have no such limit. A rule test (`tests/by_value/test_stage_folders.py`) fails when a folder under `tests/` that holds tests is run by no stage or by two. The pre-push hook and the hosted `tests (unittest)` job both run it and nothing else.

Shuttle needs Python 3.12 or newer: 3.12 is the lowest version on which the whole suite passes (one command test fails on 3.11), and it is the version the hosted job uses.

Install the development tools once (they are not runtime dependencies; the package itself uses only the standard library), preferably in a virtual environment inside the clone:

```
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Run the check:

```
./checks/all.sh
```

It prints one line per stage and a last line, `check: passed` or `check: failed: <stage>`. Exit code 0 means passed, 1 means a stage failed, 2 means the check could not run (a tool is missing; the last line names it and the install command), 3 means the argument was not recognised. The script uses the clone's `.venv/bin/python` when it exists (in a linked worktree, the main working tree's when the worktree has none; `checks/interpreter.sh` is the one lookup, shared with the hook), else `python3`; set `PYTHON` to use another interpreter. Nothing is retried.

`./checks/all.sh --fix` applies what ruff can change mechanically (safe lint fixes and the formatter, never an ignore comment or a configuration edit) and needs ruff only. It lists each file it changed (`changed: <path>`) and each file ruff could not parse or write (`failed: <path>`), then ends `fix: changed N files; now run ./checks/all.sh`, `fix: nothing to change` or `fix: failed; ...` (exit 1). It runs no types or tests; run the check afterwards. File names in this output and in the guard listing are shown escaped (a newline, a backslash, a control or direction character, or a byte that is not valid UTF-8 appears as an escape such as `\n` or `\xff`), one per line.

Switch on the pre-push hook, once per clone:

```
git config core.hooksPath .githooks
```

A push is then refused unless `./checks/all.sh` passes on the tip of each ref being pushed (the commits below a tip are not checked one by one). The hook checks out that tip into a temporary folder and runs the script there, so uncommitted changes in your folder neither pass nor fail a push (the one exception: `checks/interpreter.sh`, the interpreter lookup, is read from your folder). From a linked worktree the hook uses the worktree's own `.venv` if it has one, else the main working tree's.

## Tests

```
python3 -m unittest discover -s tests
```

The tests are sorted by seam, all run by that one command:

- `tests/by_value/`: decisions as functions over plain data, the run and the record writers on the simulated world (below), and the rule test. Where a module sits in `shuttle/` is its classification, and nothing is registered anywhere: `shuttle/core/` (sub-folders included, executor drivers in `shuttle/core/drivers/`) decides and touches nothing, `shuttle/shell/` orchestrates (calls the operations it is handed and the core), `shuttle/world/` is the real set of operations, and only `__init__.py` and `__main__.py` may sit at the package root, each kept thin (the version string; one hand-over to the shell's command line). A module under `shuttle/core/` may import only other modules under `shuttle/core/` and a short allow-list of standard library modules, and may not mention built-ins such as `open` and `print`; a module under `shuttle/shell/` is held to the same, a slightly longer allow-list, and may import the world only in `shuttle/shell/cli.py`, where the real operations are wired in; a module under `shuttle/world/` may import any standard library module, its siblings and `shuttle.core.shapes` (the operations' type) and nothing else from the package. A module anywhere else in the package fails the test, and no module may import a third-party package. The linter's ban on the libraries that reach the world applies everywhere except `shuttle/world/` (and the tests), so a shell module importing `os` is refused by both guards; that the core may not import the shell or the world is the rule test's alone, since ruff cannot ban an import in one folder only.
- `tests/command/`: the real command, the check script and the hook, run as child processes or against a temporary folder; and the real operations against the contract (below).
- `tests/rehearsal/`: test support, not part of the package. `real_run.py` lists, in every document it makes, the folder of the test's scripts and the real interpreter's installation as visible (a stand-in for a tool in a hidden folder), and the executor of a test writes only into its place. `simulated_world.py` is the whole set of operations held in memory (files as a dictionary, a clock that does not move, programs that exit, hang, hit the boundary's timer or survive its stop). It fails any operation at any call (`will_raise`), stops a file write half way (`will_stop_half_way`), runs a function at any call (`on_call`, to deliver a signal there) and is passed in where the real set would be; nothing is ever patched in by name, and a rule test refuses a test that imports `unittest.mock`, calls `patch` or assigns to an attribute of something it imported. `contract.py` is one set of cases both are held to: `tests/command/test_world_contract.py` runs it on the real operations (a temporary folder, short-lived real child processes) and `tests/by_value/test_world_contract.py` on the simulated world, so the stand-in cannot drift from the real thing. It is not `shuttle/shell/stand_ins.py`, which holds the placeholder steps of a run (delivery and the other steps not built).
- `tests/boundary/`: tests that run a real script in the real boundary: the one end-to-end test, and what is left after a child outlives its script or the command is killed hard, what a script cannot write, and the reach (`test_reach.py`: what is hidden, read-only and writable, with the test's folders under the temporary folder and under another). They skip, saying why, on a machine without the boundary (and `test_memory_limit.py`'s real cap tests also on a machine that cannot cap memory for a user scope; its refusal test runs on every machine with the boundary); where `SHUTTLE_REQUIRE_BOUNDARY` is set (the hosted runner sets it) the missing boundary is a failure, and a machine that cannot cap memory is still a skip, which the run's `report` lists. The `command` tests also start a real executor, so they need the boundary too. No test sleeps or reads a clock: `tests/ruff.toml` bans both in every test folder, a script says it is up through a pipe, and the time limit is the boundary's.

The `tests (unittest)` workflow runs the check on every pull request. Its `base check (unittest)` job also runs the base branch's copy of `checks/all.sh` against the pull request's files, so a pull request cannot pass by weakening the script, and lists in the job summary any guard files (changed, added or deleted; a moved file shows as deleted from its old path) the pull request changes: the folders and files named in `GUARD_FOLDERS` and `GUARD_FILES` in `checks/guards.py`, which are the checks, hooks, workflows and agent definitions, the lint and dependency configuration, the tests that are rules or loop an attack list or test the guard scripts themselves, and the documents that steer agents. It does not cover the workflow file or the lint configuration, which still come from the pull request; the summary is how a reviewer sees them.

## Hostile-case tables

The cases reviewers used to rebuild by hand for every pull request are kept as data in `tests/hostile/`, three tables with no logic in them: `names_table.py` (file names that break careless code: a space, a newline, a backtick, bytes that are not UTF-8, look-alikes of the guard folders; each row says whether a real filesystem can hold it), `imports_table.py` (the forms by which a module might reach what it must not: a core module reaching the shell, the entry file, the world folder or a third-party package, a shell module reaching a library that touches the world or the world folder, a world module reaching a decision, and the forms that must stay allowed; each row says whether the rule test, the linter or both refuse it) and `suppressions_table.py` (every lint-ignore spelling tried in review, whether the pinned ruff honours it, and whether the rule test must refuse it). A row says what it attacks; a row that exposed a function's bug and could not be fixed there is marked as a known gap with the reason, and its test fails if the gap closes.

- The import table drives `check_module` in `tests/by_value/test_rules.py` and, in one real ruff run, checks the "which guard" column against the real linter. The suppression table is checked against the real ruff in one run, so an upgrade that makes ruff honour a spelling the rule test lets through fails a test instead of opening a hole.
- A function in `checks/**/*.py` (every file at any depth, every definition at any nesting, `async` and methods included) that takes file names must be run against the whole names table. It is recognised by a parameter whose name contains `path`, `file`, `name`, `folder`, `root`, `link`, `source`, `changed`, `failed`, `entries`, `listing`, `target` or `location` (or has the word `dir` in it), or whose annotation mentions `Path`; the rule is `tests/by_value/test_name_functions.py`. This rule is a net with wide holes: of 24 plausible new signatures that carry a file name, it sees 12 (`p`, `entry`, `items`, `rows`, `label`, `out` and others pass unseen), and it flags words that are not names (`source` as code text). A parameter annotated only as `bool`, `int` or `float`, or a collection of those, is skipped whatever it is called: of 20 signatures with no file name, 3 are flagged (`name: str`, `source: bytes`, `entries: dict[str, int]`, whose keys can be names). The table tests of the existing functions are the real guard. A rule that flagged every parameter annotated as text or a collection of text was measured and not adopted: in `checks/` it flags 57 of 78 functions (measured once, on `ddf2008`), 26 of them already registered, and the other 31 would each need an exemption, more than the 28 registered functions. Add a test to `tests/by_value/test_names_table.py` that loops the table and states the function's invariant in its name, then register the function in `tests/hostile/registry.py`; the registered test must refer to the table. An unregistered function fails the rule test, naming the function and where to add it. A function that does not carry file names can be exempted there, with a reason (and the exemption fails if no such parameter is there).
- The tables are guard files: `tests/hostile/` and the tests that loop it are in the guard listing, and the listing adds a section, printed only when the pull request removes, changes, relabels or adds a row, or adds or closes a mark, that names each row (by table and label) that was at the base and is not at the head, each row that changed or was relabelled (old and new label), the count of rows added, each mark added and each mark closed (removed with its row kept); and, on every run, a section "Known gaps in the tables, as they stand" with every known-gap mark and its reason. A known gap needs a registered function, its name in the reason and a reason that is not empty.
- The tables cover names, import forms and lint-ignore spellings. They do not cover tree shapes (symbolic links, `.pyw` files, folder names such as `__pycache__`, `.pyi` files); those keep their hand-written tests.
- To add a case, add a row. The tests that loop a table need no change.

## The per-run report

```
./checks/report.sh
```

Prints, as Markdown, what a run of the suite looks like before a reviewer looks: tests run and skipped (with each skip's reason), total time, the eight slowest tests, time per test folder, peak memory, and for every Python file under `shuttle/` and `checks/` the statements, the statements never run and their line ranges. It is generated by that run, never checked in, and nothing fails on a number in it: it makes a lack of tests visible, it does not judge it. The report names the commit and the command it came from; on a hosted pull request run that is the head commit of the pull request, with the base it was merged with, not GitHub's merge commit. Statement counts differ between Python versions (the report prints its version), so compare a local and a hosted report by file, not number for number. The hosted job log carries one line with the test count and total time.

- It runs the whole suite once under coverage.py (a pinned development tool), so it takes longer than `./checks/all.sh`, and its times and memory include coverage's overhead. `./checks/all.sh` never runs coverage. Child processes the tests start (the real `python -m shuttle`) are counted, through coverage's `patch = subprocess` setting in `pyproject.toml`; children a test starts with an environment of its own (an explicit `env=`) are not measured, so the fix-mode, base-check and hook tests add nothing; and code that only runs from copies of the scripts in temporary trees is not counted against the originals (the report names the files under the table). Every Python file under `shuttle/` and `checks/` has a row, found by walking the folders; one coverage has no data for shows all its statements as never run.
- Peak memory is the largest resident size any one process of the run reached (from `resource.getrusage`), not a total.
- A line, or the block it opens, that is left untested on purpose ends with `# not tested: <reason>`. The report lists each with its file, line and reason; a marker with an empty reason fails the rule test, and so does the marker text inside a string or docstring (coverage would exclude that line without listing it; the report also shows a visible line if the two ever disagree). Lines without a marker are simply reported as never run.
- The hosted `tests (unittest)` job runs it after the check (a second run of the suite, which never changes whether the job passes), appends it to the job summary and keeps the same Markdown as the build artifact `report`. The `base check (unittest)` job keeps its guard file listing as the artifact `guard-files`. To find the run for a commit, run these in the clone, or add `-R <owner>/<repo>` to each: `gh run list -w tests -b <branch> --json databaseId,headSha,status`, then take the id whose `headSha` is that commit. Only the `tests` workflow holds the artifacts, a run that is not yet `completed` has none either, and no row for the commit means no run. The run is on the merge of the pull request's head with its base. Download an artifact with `gh run download <id> -n report` or `gh run download <id> -n guard-files`.
