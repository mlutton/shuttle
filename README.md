# Shuttle

Shuttle runs one program, once, inside a boundary, and writes a truthful record of how the run ended.

A caller hands Shuttle one input document. Shuttle checks it, starts one executor (an AI coding agent or a plain command), stops everything the executor started, and writes one outcome record. The caller reads that record and nothing else.

## Status

Early build. It is not usable yet, and it may not be for a while. The first increment is a skeleton: `python3 -m shuttle run <input document>` runs one plain command from start to finish and writes a request record and an outcome record. The command runs in a boundary: a systemd user scope around bubblewrap, with its own process space, the records folder bound read-only, and the time limit set as the scope's maximum runtime. The scope ends everything inside when the limit runs out (and when the run receives a signal: SIGINT, SIGTERM, SIGHUP, SIGQUIT, SIGUSR1, SIGUSR2 or SIGALRM), the run stops it by name and sees it empty, and reads from the scope why it ended; a reason it cannot read is "execution failed", never a guess. The time limit is a number of seconds from one microsecond to 10^9 (about 31 years): the scope's timer takes whole microseconds, and a value that rounds to zero would mean no limit at all. Arguments reach the command byte for byte: the scope tool expands `$` in the command it is given, so every `$` is doubled on the way in (the option that turns that off needs systemd 254). The boundary needs `systemd-run`, `systemctl` and `bwrap` on the machine. The run form and the check form exist (stop and status do not). The place and its two fingerprints are real (see "The place and the fingerprints"); delivery and the rest are stand-ins or not built, and a receipt field fed by a stand-in says "not built". The code and its tests are published as they are written, so the tests are the best account of what works today.

## What it will promise

- Every run ends with exactly one of six endings: ended by itself, time limit, stopped from outside, asked for a human, could not start, execution failed.
- What Shuttle observed is kept apart from what the executor says about its own work.
- Once the ending is known, nothing prevents a record carrying that ending.
- A request record is written before anything starts and an outcome record when the run ends, so the two together are the trace of the run.
- Each vendor's tool sits behind an executor driver, so a run looks the same from outside whichever tool did the work.

## Shape

- Outside: a command-line tool with four forms (run, check, stop, status).
- Inside: functions over plain data, in three folders. Each decision is a pure function in `shuttle/core/`. The code that gathers facts, hands them to the core and acts on the answer is `shuttle/shell/`; it touches nothing itself. Everything Shuttle does to the world (files, processes, the boundary's scope, the clock, signals, the environment, who and what it is, and the place's git repository) is one small set of operations, a record of functions typed in `shuttle/core/shapes.py` (`Operations`) and passed in; the real set is `shuttle/world/`, thin and holding no decisions. The command line wires the real set in (`shuttle/shell/cli.py`) and the process's arguments and standard streams come from the world's entry (`shuttle/world/real.py`).
- Python, standard library only.

## Refusals and the check form

- A run that cannot start ends `could_not_start` with a reason code and the step that failed. The checks are pure functions in `shuttle/core/refusals.py`, tested as tables (`tests/by_value/test_refusals.py`); the shell (`shuttle/shell/input_checks.py`, `gates.py`) gathers the facts they judge: a reference file's hash and size, whether the statement location is taken, a gate's exit code.
- The input document carries optional `instruction` with `instruction_hash` (sha256 of the instruction's UTF-8 text, given together), `references` (name, path, hash, size, hash_source), `gates` (name, command, arguments, limit_seconds), `statement_location`, `reach` (reserved: any content is refused) and `place` (required: the path of a linked working copy of the caller's repository, see below). Not yet built from the design: the destination and branch checks, the records-location mismatch check (the design does not say how Shuttle can know a repository's records location, so there is nothing to compare yet), folder references (a folder is refused as missing, and the message says it is a folder), and handing the instruction to an executor (the notice below is built and tested by value; the command driver reads no instruction yet).
- Kinds are read from two files shipped with the code, `shuttle/data/kinds_with_statement.txt` and `shuttle/data/kinds_without_statement.txt`; a kind on neither is refused, and so is a run whose files cannot be read. A kind that expects a statement needs a `statement_location` that does not exist yet; a kind that expects none and is given one is refused (`unknown_field`).
- Gates run in order before the executor starts, each with PATH only in its environment (and what systemd itself sets, such as `INVOCATION_ID`), each in a systemd user scope of its own with its limit as the scope's maximum runtime: nothing in the command times a gate. After a gate the scope is stopped by name, seen empty and forgotten, and why it ended is read from it. Exit 0 is yes, exit 1 is no; any other exit, a passed limit, a scope that was not seen settled or a failed start is failed. The scope's tool exits 1 when it cannot make the scope, which would read as a no, so the gate's command is started through one line of shell that says on a pipe that it is about to start; a gate that never said so is failed. The first answer that is not yes refuses the run, and its name and answer are the reason text.
- The request id may be left out: one is generated and printed first. An id is used once: a run is refused when its request record or its outcome record exists, and neither is touched. That refusal, a document too broken to form a header, and (awaiting the owner's decision) a document holding a credential-like environment value write no record at all, print one line on standard error, and exit non-zero; the last is refused before the id is claimed, so no record keeps the value and the id is not spent. The check form still reports `credential_like_value` for it.
- `python3 -m shuttle check <input document>` runs every check a run would make, including the gates and whether the id is used and the records location is a folder that exists and can be written, and launches no executor (it does start the gates, which are read-only by their nature), writes no record and claims no id. It prints the request id, then (when it found a refusal) the outcome record the run would have written, on one line, then `check: no refusal found` or `check: refused: <reason>`, then a last line saying that passing is not a promise. Exit 0 means the check ran to its end, passing or refusing; non-zero means the document could not be read far enough to check.

## The place and the fingerprints

- The input document's `place` is the path of a linked working copy of the caller's repository, made by the caller for this run. A run is refused, before anything starts and in the check form alike (reason, failed step `input_check`), when the place is not a folder that is there (`place_missing`; a document with no `place` is the same), is not the top of a git working copy with at least one commit (`place_not_a_git_checkout`; a folder inside a checkout is not one), has a tracked file that carries a `filter` attribute, from `.gitattributes` or the repository's `info/attributes` (`place_has_filter_attribute`; filter drivers are not supported and never run, so such a place is refused whatever the index's timestamps are, with one such path named), holds a repository of its own below its top, whether git ignores it or not (`place_has_nested_repository`, named before the uncommitted file git also reports for it), or has uncommitted, staged or new unignored files (`place_has_uncommitted_changes`). The place is looked at again just before the executor starts, since the gates ran in between: a place that is no longer clean is a `freeze_failed` at `opening_freeze`.
- The opening fingerprint is the place's own commit. No commit is made at the start. The closing freeze is one commit of the place's files as they are, made by Shuttle to the reference `refs/shuttle/freeze/<request id>` in the place's repository, with the opening commit as its parent, under the name "Shuttle", no address and a fixed date, so the same files give the same commit. It is taken only when the executor's boundary was seen empty. It holds every file that the ignore rules of the working files at the time of the freeze do not exclude (the design says the opening commit's rules; the owner is deciding, and today's behaviour is the working files', so a script that ignores a file as it writes it leaves it out of the freeze), whatever the place's own history says: a script that makes its own commits, moves the branch or resets it does not move the closing fingerprint, and a commit made by the executor is never the freeze. Files equal to the opening commit's give the opening commit itself (nothing is made), the receipt says `changed_nothing`, and the counts are zero; otherwise the receipt counts files added, changed (a change of type counts) and deleted against the opening commit. A link is frozen as a link and never followed; a repository cloned into the place during the run is frozen as one entry naming its commit; a file that cannot be read, a folder that git cannot enter (its files would otherwise be left out without a word), or any other failure of git, is a failed closing freeze (`execution_failed`, `closing_freeze_failed`, failed step `closing_freeze`) with the opening fingerprint only.
- No command from any configuration runs in Shuttle's git work: not a filter driver (`clean`, `smudge` or `process`) defined in the repository, added to it by the executor during the run, or defined at user or system level. The place check reads attributes (which runs nothing) before it compares anything. The freeze adds the files in a scratch git directory with no configuration, whose working tree is the place and whose objects are the place's, so no driver exists there to run, and a file the script added under a filter attribute is frozen as its bytes on disk; only `update-ref` runs in the place's own repository. The freeze therefore reads none of the repository's own settings (such as `core.filemode`); it does read the place's `info/attributes` and `info/exclude`. Every git call is given exactly the environment `shuttle/core/place.py` builds: PATH only from the caller's, no global or system configuration, no hooks, no signing, no editor, no prompts, no ignore file or attributes of the caller's, the place's own settings for those overridden, the neutral identity, and no write to the caller's index when only looking. The freeze uses plumbing on a temporary index of its own, so the caller's branch, index and settings are untouched; its only write to the repository is its commit's objects and its reference. Freeze references stay in the repository: one per run that changed something, never removed, and they show in `git for-each-ref`, in `git log --all` and in a mirror push (`git push --mirror`; not in `--all` or `--tags`), so a caller who mirrors publishes the frozen files.
- The freeze's git work is one command run to its end in a scope of its own, with the limit on the scope, the way a gate is run: nothing in the command times it. Its limit is the document's optional `freeze_limit_seconds` (the same bounds as the time limit), and the run's own `time_limit_seconds` when that is left out: the design gives no value for it, so none is invented (awaiting the owner).
- The executor's working directory is the place (bubblewrap's `--chdir`).
- Git is reached only through the `git` group of the operations (`look_at_place`, `freeze`); the real set is `shuttle/world/git.py`, the simulated one is held to it by the contract cases.

## The statement and the references

- The statement's schema is data, defined once in `shuttle/data/statement_schema.json`, so a second program (the check on a builder's hand-off) can read the same file. Its fields: `claim` (one of `done`, `partly_done`, `blocked`, `not_done`), `summary` (text), `evidence` (a list of items, each a `claim` and a `command` to run, not a pasted log), `not_tested` (a list of text, empty when nothing was left out) and `feedback` (text, on the input). Every field is required and no other is allowed. `shuttle/core/statement.py` judges a statement's bytes against that data by hand (no library), and `tests/by_value/test_statement.py` is the table of accepted and rejected statements.
- After the run, the file the executor left at `statement_location` is copied byte for byte to `<request id>.statement.kept` beside the records, and that copy is hashed and judged. Execution never tidies or completes it. The receipt's `statement_state` is `none` (the state: nothing was left), `right_shape` or `wrong_shape`; `statement_hash` and `statement_location` are the kept copy's; `claim` is the claim word as written when the shape is right and `none` otherwise. Where a wrong-shaped statement is reported beyond that state is not specified, so nothing more is built. A file that could not be kept or read leaves the four fields `cannot tell`. The statement is copied, not moved: the original stays at the location, and a location is used once (a second run naming it is refused as occupied). Only a regular file is kept: a link (never followed), a named pipe, a device, a socket or a folder at the location reads `wrong_shape` and nothing is copied.
- The notice (`shuttle/core/notice.py`, version `NOTICE_VERSION` in `fixed.py`) is added to the instruction of a kind that expects a statement and not to one that expects none: where and how to write the statement, where each reference is, that a reference wins over a file of the same name in the place, and that the executor cannot commit in the place. It is a pure function tested by value; nothing hands it to an executor yet, because the command driver reads no instruction.
- Every reference's path is bound read-only in the boundary beside the records location. The receipt's `reference_hashes` is each reference's hash by name, as the check before the start found it; `none` when the run was refused or has no references.

## The records

Two records are written per run, both JSON:

- A request record (a header, and `input`, the exact text the caller gave, nothing rewritten or dropped, a duplicate key included; the receipt's `input_hash` is over those same bytes, so it can be checked from the record alone) before anything starts, and an outcome record (a header, and the receipt) when the run ends.
- Every field of the receipt is a pair, `{"state": ..., "value": ...}`: the state says how the value is known, so a field whose own text is the word "none" is not mistaken for the state "none".
- The four states, in the one list of fixed values (`shuttle/core/fixed.py`, `STATES`), are `value` (execution looked and found this), `none` (it looked and there is nothing), `cannot tell` (it could not look) and `not built` (the step behind the field is still a stand-in; when the last stand-in is replaced, the state is removed from the list).
- Only the state `value` carries a value; the others carry `null`.
- The executor's exit code is what bubblewrap reports for it, and bubblewrap reports a child killed by signal `n` as `128 + n`, the same as a script that exits with that number; its status report (`--json-status-fd`) uses the same encoding, so nothing the boundary offers tells the two apart. The receipt keeps the exit code as observed and says `cannot tell` for `signal` in every run whose executor ran in the boundary; it never reads a signal out of a number. A run in which the executor never started (bubblewrap's report has no `child-pid`: a tool missing or refused, no user manager, no user namespaces) ends as could not start, reason `launch_failed`, with no exit code and no signal.
- The receipt has four groups, keyed `ending` (the ending, its reason and the receipt's id), `execution` (what execution itself saw, with its own version and the host), `executor_driver` (what the executor driver observed) and `executor` (what the executor said).
- The input document and the records carry separate version numbers, `INPUT_VERSION` (the document's `format_version`) and `RECORD_VERSION` (each header's `record_version`), in `shuttle/core/fixed.py`; each is checked on its own, and the first version makes no compatibility promise.
- Records sit beside each other in the records location, named `<request id>.<kind>.json`, with the four kinds (`request`, `outcome`, `stop`, `liveness`) in the one list of fixed values (`RECORD_KINDS`) and every name made in one place (`record_name`).
- Only the request and outcome records are written; the names of the stop record and the liveness file are reserved and nothing more is defined for them.
- A request id cannot hold a dot.
- A receipt is built only from pairs: a bare string where a pair belongs, or a field left out, is refused.
- A step says "looked, found nothing" by returning an empty value (an empty text, list or dictionary); a key it leaves out, or `None`, reads as "cannot tell".
- What execution observed is turned into pairs without ever handing the builder one it refuses: an empty text (an empty host name, say) is `none`, and anything JSON cannot hold, or a number that is not finite, is `cannot tell` for that field alone.
- If the builder still refuses, the run says so in one line on standard error, naming the fields, and writes the minimal receipt (the ending, and `cannot tell` for every other field).
- A value whose state is `value` is plain JSON, and in the ending group the words `none`, `cannot tell` and `not built` are said by the state, never held as a value.
- A key that holds a quantity names its unit: `duration_executor_seconds`, `processor_time_seconds`, `peak_memory_bytes`.

## Checking a change

One script decides whether a change is sound: lint (ruff, including a limit of three nested blocks and a ban on importing any library that reaches the world anywhere under `shuttle/` except `shuttle/world/`, and on the core importing the entry file; the other import rules between the folders are the rule test's, in the tests), format check (ruff), strict types (mypy, over `shuttle/`), the by-value tests (`tests/by_value`, under a 20 second budget that keeps the logic tests fast) and the tests that start real processes (`tests/command` then `tests/boundary`, a stage of their own under a 120 second budget that ends a test that never returns; it stops at the first folder that fails, so a failure in the first means the second did not run). The real-process tests are bounded in time by that budget; the tests that hand the command an input without an end run under the resource limits of `tests/rehearsal/real_run.py`. The pre-push hook and the hosted `tests (unittest)` job both run it and nothing else.

Shuttle needs Python 3.12 or newer: 3.12 is the lowest version on which the whole suite passes (one command test fails on 3.11), and it is the version the hosted job uses.

Install the development tools once (they are not runtime dependencies; the package itself uses only the standard library), preferably in a virtual environment inside the clone:

```
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Run the check:

```
./checks/all.sh
```

It prints one line per stage and a last line, `check: passed` or `check: failed: <stage>`. Exit code 0 means passed, 1 means a stage failed, 2 means the check could not run (a tool is missing; the last line names it and the install command), 3 means the argument was not recognised. The script uses the clone's `.venv/bin/python` when it exists (in a linked worktree, the main working tree's when the worktree has none; `checks/interpreter.sh` is the one lookup, shared with the hook), else `python3`; set `PYTHON` to use another interpreter. Nothing is retried.

`./checks/all.sh --fix` applies what ruff can change mechanically (safe lint fixes and the formatter, never an ignore comment or a configuration edit) and needs ruff only. It lists each file it changed (`changed: <path>`) and each file ruff could not parse or write (`failed: <path>`), then ends `fix: changed N files; now run ./checks/all.sh`, `fix: nothing to change` or `fix: failed; ...` (exit 1). It runs no types or tests; run the check afterwards. File names in this output and in the guard listing are shown escaped (a newline, a backslash, a control or direction character, or a byte that is not valid UTF-8 appears as an escape such as `\n` or `\xff`), one per line.

Switch on the pre-push hook, once per clone:

```
git config core.hooksPath .githooks
```

A push is then refused unless `./checks/all.sh` passes on each commit being pushed. The hook checks out that commit into a temporary folder and runs the script there, so uncommitted changes in your folder neither pass nor fail a push (the one exception: `checks/interpreter.sh`, the interpreter lookup, is read from your folder). From a linked worktree the hook uses the worktree's own `.venv` if it has one, else the main working tree's.

## Tests

```
python3 -m unittest discover -s tests
```

The tests are sorted by seam, all run by that one command:

- `tests/by_value/`: decisions as functions over plain data, the run and the record writers on the simulated world (below), and the rule test. Where a module sits in `shuttle/` is its classification, and nothing is registered anywhere: `shuttle/core/` (sub-folders included, executor drivers in `shuttle/core/drivers/`) decides and touches nothing, `shuttle/shell/` orchestrates (calls the operations it is handed and the core), `shuttle/world/` is the real set of operations, and only `__init__.py` and `__main__.py` may sit at the package root, each kept thin (the version string; one hand-over to the shell's command line). A module under `shuttle/core/` may import only other modules under `shuttle/core/` and a short allow-list of standard library modules, and may not mention built-ins such as `open` and `print`; a module under `shuttle/shell/` is held to the same, a slightly longer allow-list, and may import the world only in `shuttle/shell/cli.py`, where the real operations are wired in; a module under `shuttle/world/` may import any standard library module, its siblings and `shuttle.core.shapes` (the operations' type) and nothing else from the package. A module anywhere else in the package fails the test, and no module may import a third-party package. The linter's ban on the libraries that reach the world applies everywhere except `shuttle/world/` (and the tests), so a shell module importing `os` is refused by both guards; that the core may not import the shell or the world is the rule test's alone, since ruff cannot ban an import in one folder only.
- `tests/command/`: the real command, the check script and the hook, run as child processes or against a temporary folder; and the real operations against the contract (below).
- `tests/rehearsal/`: test support, not part of the package. `simulated_world.py` is the whole set of operations held in memory (files as a dictionary, a clock that does not move, programs that exit, hang, hit the boundary's timer or survive its stop). It fails any operation at any call (`will_raise`), stops a file write half way (`will_stop_half_way`), runs a function at any call (`on_call`, to deliver a signal there) and is passed in where the real set would be; nothing is ever patched in by name, and a rule test refuses a test that imports `unittest.mock`, calls `patch` or assigns to an attribute of something it imported. `contract.py` is one set of cases both are held to: `tests/command/test_world_contract.py` runs it on the real operations (a temporary folder, short-lived real child processes) and `tests/by_value/test_world_contract.py` on the simulated world, so the stand-in cannot drift from the real thing. It is not `shuttle/shell/stand_ins.py`, which holds the placeholder steps of a run (set-up, delivery).
- `tests/boundary/`: tests that run a real script in the real boundary: the one end-to-end test, and what is left after a child outlives its script or the command is killed hard, and what a script cannot write. They skip, saying why, on a machine without the boundary; where `SHUTTLE_REQUIRE_BOUNDARY` is set (the hosted runner sets it) the missing boundary is a failure. The `command` tests also start a real executor, so they need the boundary too. No test sleeps or reads a clock: `tests/ruff.toml` bans both in every test folder, a script says it is up through a pipe, and the time limit is the boundary's.

The `tests (unittest)` workflow runs the check on every pull request. Its `base check (unittest)` job also runs the base branch's copy of `checks/all.sh` against the pull request's files, so a pull request cannot pass by weakening the script, and lists in the job summary any guard files (changed, added or deleted; a moved file shows as deleted from its old path) the pull request changes: the folders and files named in `GUARD_FOLDERS` and `GUARD_FILES` in `checks/guards.py`, which are the checks, hooks, workflows and agent definitions, the lint and dependency configuration, the tests that are rules or loop an attack list or test the guard scripts themselves, and the documents that steer agents. It does not cover the workflow file or the lint configuration, which still come from the pull request; the summary is how a reviewer sees them.

## Hostile-case tables

The cases reviewers used to rebuild by hand for every pull request are kept as data in `tests/hostile/`, three tables with no logic in them: `names_table.py` (file names that break careless code: a space, a newline, a backtick, bytes that are not UTF-8, look-alikes of the guard folders; each row says whether a real filesystem can hold it), `imports_table.py` (the forms by which a module might reach what it must not: a core module reaching the shell, the entry file, the world folder or a third-party package, a shell module reaching a library that touches the world or the world folder, a world module reaching a decision, and the forms that must stay allowed; each row says whether the rule test, the linter or both refuse it) and `suppressions_table.py` (every lint-ignore spelling tried in review, whether the pinned ruff honours it, and whether the rule test must refuse it). A row says what it attacks; a row that exposed a function's bug and could not be fixed there is marked as a known gap with the reason, and its test fails if the gap closes.

- The import table drives `check_module` in `tests/by_value/test_rules.py` and, in one real ruff run, checks the "which guard" column against the real linter. The suppression table is checked against the real ruff in one run, so an upgrade that makes ruff honour a spelling the rule test lets through fails a test instead of opening a hole.
- A function in `checks/**/*.py` (every file at any depth, every definition at any nesting, `async` and methods included) that takes file names must be run against the whole names table. It is recognised by a parameter whose name contains `path`, `file`, `name`, `folder`, `root`, `link`, `source`, `changed`, `failed`, `entries`, `listing`, `target` or `location` (or has the word `dir` in it), or whose annotation mentions `Path`; the rule is `tests/by_value/test_name_functions.py`. This rule is a net with wide holes: of 24 plausible new signatures that carry a file name, it sees 12 (`p`, `entry`, `items`, `rows`, `label`, `out` and others pass unseen), and it flags words that are not names (`source` as code text). A parameter annotated only as `bool`, `int` or `float`, or a collection of those, is skipped whatever it is called: of 20 signatures with no file name, 3 are flagged (`name: str`, `source: bytes`, `entries: dict[str, int]`, whose keys can be names). The table tests of the existing functions are the real guard. A rule that flagged every parameter annotated as text or a collection of text was measured and not adopted: in `checks/` it flags 57 of 78 functions (measured once, on `ddf2008`), 26 of them already registered, and the other 31 would each need an exemption, more than the 28 registered functions. Add a test to `tests/by_value/test_names_table.py` that loops the table and states the function's invariant in its name, then register the function in `tests/hostile/registry.py`; the registered test must refer to the table. An unregistered function fails the rule test, naming the function and where to add it. A function that does not carry file names can be exempted there, with a reason (and the exemption fails if no such parameter is there).
- The tables are guard files: `tests/hostile/` and the tests that loop it are in the guard listing, and the listing adds a section, printed only when the pull request removes, changes, relabels or adds a row, or adds or closes a mark, that names each row (by table and label) that was at the base and is not at the head, each row that changed or was relabelled (old and new label), the count of rows added, each mark added and each mark closed (removed with its row kept); and, on every run, a section "Known gaps in the tables, as they stand" with every known-gap mark and its reason. A known gap needs a registered function, its name in the reason and a reason that is not empty.
- The tables cover names, import forms and lint-ignore spellings. They do not cover tree shapes (symbolic links, `.pyw` files, folder names such as `__pycache__`, `.pyi` files); those keep their hand-written tests.
- To add a case, add a row. The tests that loop a table need no change.

## The per-run report

```
./checks/report.sh
```

Prints, as Markdown, what a run of the suite looks like before a reviewer looks: tests run and skipped (with each skip's reason), total time, the eight slowest tests, time per test folder, peak memory, and for every Python file under `shuttle/` and `checks/` the statements, the statements never run and their line ranges. It is generated by that run, never checked in, and nothing fails on a number in it: it makes a lack of tests visible, it does not judge it. The report names the commit and the command it came from; on a hosted pull request run that is the head commit of the pull request, with the base it was merged with, not GitHub's merge commit. Statement counts differ between Python versions (the report prints its version), so compare a local and a hosted report by file, not number for number. The hosted job log carries one line with the test count and total time.

- It runs the whole suite once under coverage.py (a pinned development tool), so it takes longer than `./checks/all.sh`, and its times and memory include coverage's overhead. `./checks/all.sh` never runs coverage. Child processes the tests start (the real `python -m shuttle`) are counted, through coverage's `patch = subprocess` setting in `pyproject.toml`; children a test starts with an environment of its own (an explicit `env=`) are not measured, so the fix-mode, base-check and hook tests add nothing; and code that only runs from copies of the scripts in temporary trees is not counted against the originals (the report names the files under the table). Every Python file under `shuttle/` and `checks/` has a row, found by walking the folders; one coverage has no data for shows all its statements as never run.
- Peak memory is the largest resident size any one process of the run reached (from `resource.getrusage`), not a total.
- A line, or the block it opens, that is left untested on purpose ends with `# not tested: <reason>`. The report lists each with its file, line and reason; a marker with an empty reason fails the rule test, and so does the marker text inside a string or docstring (coverage would exclude that line without listing it; the report also shows a visible line if the two ever disagree). Lines without a marker are simply reported as never run.
- The hosted `tests (unittest)` job runs it after the check (a second run of the suite, which never changes whether the job passes), appends it to the job summary and keeps the same Markdown as the build artifact `report`. The `base check (unittest)` job keeps its guard file listing as the artifact `guard-files`. To find the run for a commit, run these in the clone, or add `-R <owner>/<repo>` to each: `gh run list -w tests -b <branch> --json databaseId,headSha,status`, then take the id whose `headSha` is that commit. Only the `tests` workflow holds the artifacts, a run that is not yet `completed` has none either, and no row for the commit means no run. The run is on the merge of the pull request's head with its base. Download an artifact with `gh run download <id> -n report` or `gh run download <id> -n guard-files`.
